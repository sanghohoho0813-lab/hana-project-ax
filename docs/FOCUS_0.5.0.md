## 2. 무엇이 바뀌었나 (0.5.0)

### 우선순위

1. **막힘 · 변수 조기 보고와 본사 빠른 지원.** 중간 확인, 확인 필요 목록, 지원 요청 우선 순서가 여기에 해당한다.
2. **안전점검 3단계 착용 사진.** 단계 누락 표시와 측정 10이 여기에 해당한다.
3. **후속 일정 영향(연쇄 위험).** 기존 엔진을 그대로 쓰고 보조 지표로 표시한다.

### 기능

**조기 확인 규칙** — `src/lib/pilot/watch.ts`, `조기 확인 규칙 0.1 (2026-11-16 초안)`
- 규칙 기반이며 AI 예측이 아니다. 새 기록을 만들지 않는다.
- 기존 기록인 작업 시작 · 예상 종료 보고 · 작업 종료 · 문제 보고만 본다.
- 판정은 넷이다.
  - **중간 확인**: 작업 시작 뒤 예정 소요의 절반(최소 20분)이 지났는데 진행 보고(예상 종료 보고)가 없다.
  - **예정 넘김**: 예상 종료를 지났는데 새 보고도 문제 보고도 없다.
    - 예상 종료는 작업 시작 뒤 마지막으로 보고한 예상 종료다.
    - 보고가 없으면 예정 소요시간 유지 가정을 쓴다. 엔진과 같은 가정이다.
  - **지원 중**: 처리 중인 문제 보고가 있다. 본사가 이미 알고 있다는 뜻이다.
  - 나머지는 정상이다.

**현장 직원 휴대폰** — "지금 할 일" 카드
- 중간 확인일 때: "작업 시작 40분째예요 — 예정대로 되고 있나요?"
  - **막혔어요**: 문제 보고를 바로 연다.
  - **예정대로**: 예상 종료 보고로 즉시 기록한다. 본사가 '언제 확인했는지' 남는다.
  - **늦어져요**: 새 예상 종료를 보낸다.
- 예정 넘김일 때: "예상 종료가 N분 지났어요". 버튼은 막혔어요와 늦어져요 둘이다.
- 평소 안내 문장도 바꿨다. "막히면 혼자 붙잡지 말고 바로 '문제 보고'를 누르세요"를 앞에 둔다.
- 안전점검 버튼에 지금 낼 단계를 표시한다.
- 작업을 마친 현장에서 빠진 점검은 '본사에서 온 소식'에 알린다.

**관리자 대시보드**
- 맨 위에 **확인 필요 — 연락 없이 늦어지는 현장**을 둔다.
  - 현장마다 "전화 확인 → 대리 보고" 바로가기가 있다.
  - 대리 보고는 기존 기능이며, 전화로 확인한 문제를 발견·보고 시각과 함께 남긴다.
- 핵심 숫자에 **확인 필요 현장**을 추가했다.
- '위험도 높은 현장'은 **후속 일정 영향**으로 이름을 바꾸고 맨 뒤로 옮겼다.
- 안전점검 칸이 연쇄 위험보다 앞에 오고 **단계 누락**을 센다.
- '최근 처리 결과'는 숫자 칸에서 빼고 오른쪽 목록 머리에 해결 · 그 밖 수를 보여 준다.

**우선 처리 순서** — `rankCases`
- 바뀐 순서: 안전 위험 · 긴급 → **본사 확인 전 → 지원 요청(숙련 기술자·장비·원격)** → 후속 일정 영향(엔진 계산) → 오래 기다린 순.
- 0.4까지는 엔진의 후속 위험 수가 미접수보다 앞이었다.
- 엔진 계산 자체는 같다.

**안전관리 화면**
- **현장별 3단계 현황** 표를 넣었다: 작업 전 · 작업 중 · 마무리.
- 칸마다 제출·확인 상태, 누락, 낼 차례를 보여 준다.

**성과 측정 화면**
- **핵심 지표** 안내를 넣었다.
  - 측정 1: 발견 → 보고. 혼자 붙잡은 시간이다.
  - 측정 2·3: 보고 → 확인 → 지원 결정.
  - 측정 10: 안전점검 3단계 제출.
- **측정 10**을 새로 넣었다. 작업을 마친 현장 가운데 3단계를 모두 낸 현장 수, 단계별 제출 수, 관리자 확인 수를 보여 준다.

### 바뀌지 않은 것

- 연쇄위험 판단엔진(특허 연계)의 계산과 규칙 버전.
- DB 스키마 · RLS · 인증 · 기록. 새 마이그레이션이 없다.
- 운영 SQL 묶음은 버전 글자만 0.5.0으로 바뀐다. 0.3.2 이후 묶음을 이미 적용했다면 다시 적용할 필요가 없다.
- 안전점검 3단계 착용 사진 필수와 관리자 육안 확인은 0.3에서 이미 구현돼 있었다. 이번에는 '빠진 단계'를 찾아 보여 주는 것만 더했다.
- 실증 홈(브라우저 기록 데모)의 예시 2건이 원래 통화 내용과 같은 이야기다.
  - 설치환경 문제 → 숙련 기술자 파견.
  - 장비 부족 → 장비 전달.

## 3. '위험분석 AX'로 설명할 때 (서술 제안)

신청 분야는 이미 위험분석 AX로 정해져 있다. 그 범위 안에서 다루는 위험을 아래 셋으로 설명할 수 있다. 확정 문안이 아니라 초안이다.

| 위험 | 무엇으로 잡나 | 전후 비교에 쓰는 기록 |
| --- | --- | --- |
| ① 현장 작업 지체 위험 (막힘 · 변수 미보고) | 조기 확인 규칙(중간 확인 · 예정 넘김) → 문제 보고 → 본사 지원 결정 | 측정 1 발견→보고, 측정 2·3 보고→확인→지원 결정 |
| ② 안전 미준수 위험 (장구 미착용) | 3단계 착용 사진 + 관리자 육안 확인 + 단계 누락 표시 | 측정 10 안전점검 3단계 제출 |
| ③ 후속 일정 영향 위험 | 기존 연쇄위험 판단엔진 (문제 보고의 예상 종료 → 다음 현장 영향 계산) | 측정 5·6 (보조) |

**도입 전 자료(비교 기준)**
- 통화에서 들은 도입 전 방식은 "전화해서 확인"이다.
- 도입 전 값은 원자료가 있을 때만 '실제 과거 현장정보 재현'으로 넣는다.
  - 원자료 예: 업무일지 · 통화기록 · 메신저.
  - 원자료 이름은 필수다.
- 원자료가 없으면 '가상 시나리오'로만 넣는다.
- 이 셋을 섞어 쓰지 않는다.

## 4. 기준값 · 확인할 것 (아직 확인 안 됨)

아래는 구본석 이사께 물어볼 질문이다. 확인되기 전에는 '확인됨'으로 쓰지 않는다.

1. 중간 확인 시점(예정 소요의 절반, 최소 20분)이 현장 감각에 맞는가?
2. 신규 직원을 따로 표시할 필요가 있는가?
   - 지금은 직원 정보에 경력 구분이 없다.
   - 넣으려면 DB 변경이 필요하므로 따로 승인받아 진행한다.
3. 기관마다 다른 안전 규칙(점검 항목)을 회사 기준으로 확정할 수 있는가?
   - 지금 항목은 초안이다: `src/lib/pilot/safety.ts`.
4. '예정대로' 응답을 하루 몇 번까지 물어도 현장에서 번거롭지 않은가?
   - 지금은 현장마다 한 번 묻는다. 진행 보고를 한 번 하면 그 예상 종료까지는 다시 묻지 않는다.
