# 0.6.1 — Supabase 운영 연결 전 최종 안정화 (2026-11-18)

대상: 실사용 프로그램 `/pilot` (현장기사 휴대폰 · 관리자 PC). 실증판(브라우저 저장)은 바꾸지 않았다.
원칙: 문제를 코드에서 **먼저 재현하거나 확인**하고 고친다. 고친 것마다 회귀 시험을 붙인다. 문제가 확인되지 않은 곳은 손대지 않는다.
바꾸지 않은 것: **판단엔진**(`chain-risk/1.1.0` · `state-deviation/1.0.0` · `response-priority/1.0.0`) · **DB 구조 · RLS · Storage 권한** · 인증 · 오프라인 보내기 대기열. 새 마이그레이션은 없다. 운영 SQL 묶음은 버전 글자만 0.6.1로 바뀌었다.

> 이 문서의 '확인'은 이 개발 환경(로컬 Supabase · 한 컴퓨터의 브라우저 세션)에서 한 자체 시험이다. 실제 휴대폰 · 운영 Supabase · 이동통신망에서는 아직 확인하지 않았다 (4장).

## 1. 잘 되어 있어 그대로 둔 것

| 항목 | 확인한 내용 |
|---|---|
| 판단엔진 결과의 일관성 | 같은 입력이면 같은 결과 · 취소 일정 · 빠진 기록 · 잘못된 시각 처리 시험이 이미 있고 통과. 엔진 계산식에서 실제 오류를 찾지 못해 **고치지 않았다** |
| 같은 요청 한 번만 | 문제 보고 · 단계 기록 · 사진 연결(`attach_case_photo` · `attach_safety_photo`)이 요청 번호(op_id)로 중복을 막는다 |
| 오프라인 보내기 대기열 | 끊긴 동안 누른 기록을 보관 후 다시 보냄 (`queue.ts`) — 변경 없음 |
| 입력 중 화면 갱신 보호 | 입력 · 터치 뒤 8초는 자동 갱신으로 화면을 다시 그리지 않음 — 그대로 유지 |
| 관리자 '적합' 확인 | 살아 있는 사진이 없으면 '적합(육안)' 버튼이 꺼져 있음 — 이미 있었음 |
| 급한 위험 안내 | '작업 중지 · 직접 전화' 안내 — 그대로 유지 |
| 판단 기준값 표기 | 등급 기준(10 · 30분)과 조기 확인 기준(절반 · 20분)은 '설정값 · 초안'으로 이미 적혀 있음 |

| C-1 | 현장 흐름 · 안전 | 시작 전 점검에 **'미흡'이 남아 있어도** 작업 시작을 바로 눌렀다 (점검이 있으면 묻지 않음) | 미흡이 남았고 관리자 '조치 완료'가 아니면 한 번 더 묻는다. '작업 시작 안 함' / '그래도 작업 시작' — 막지는 않음 | `stability.mjs` C |
| D-1 | 조기 확인 | **작업 시작을 나중에 사후 입력하면, 그 전에 보낸 진행 보고(예상 종료)를 무시했다** — 기록 순서로 비교했기 때문. 관리자 화면에 거짓 '중간 확인 · 예정 넘김'이 뜰 수 있었다. 실패하는 시험으로 먼저 재현 | 기록 순서가 아니라 **실제 발생시각**으로 비교 — 관리자(`watchInputOf`) · 현장(`lastReportAfterStart`) 둘 다 | `watch.test.ts` +5 (사후 입력 · 시작 전 보고 제외 · 같은 입력 같은 결과 · 자정 근처) |

고친 곳은 모두 엔진 밖이다. D-1의 `watch.ts`는 0.5에서 추가한 표시 규칙이며, 엔진 계산에는 영향이 없다.

**알려진 한계 (고치지 않음 · 운영 기준 결정 필요)**
- 조기 확인(중간 확인 · 예정 넘김)은 **오늘 날짜 화면에서만** 계산한다. 자정을 넘겨 계속되는 작업은 다음 날 화면에 뜨지 않는다. 시각은 23:59에서 멈추고, 기기 시계가 작업 시작보다 앞서면 경과를 0분으로 본다 (시험으로 확인).
- 조기 확인 기준(예정 소요의 절반 · 최소 20분)과 등급 기준(10 · 30분)은 **초안 설정값**이다. 회사 운영 기준으로 확정해야 한다.
- 자동 갱신은 **주기 확인**(문제·지원 10초 · 관리자 대시보드 · 현장 15초 안팎)이다. 실시간 푸시가 아니다.

## 5. Supabase 프로젝트를 만든 뒤 작업 순서

모든 운영 인프라 작업은 사용자(하나정보통신)가 직접 한다. 이 저장소는 운영 Supabase · Vercel 설정을 바꾸지 않는다.

1. **Supabase 새 프로젝트** (서울 지역) — 설정 가이드 1장 `docs/FIELD_SYSTEM_SETUP_GUIDE.md`
2. **DB 구조 적용**: `supabase/production/01_apply_all_migrations.sql`(0.6.1) → `02_set_judge_secret.sql` → `03_bootstrap_admin.sql` → `04_verify_setup.sql` (13항목 정상, `schema_bundle`이 `0.6.1 · 마이그레이션 6개`) — 가이드 2장. **개발용 `seed.sql`은 넣지 않는다.**
3. **로그인 설정 · 계정** (공개 가입 끄기 · 주소 · 2단계 인증) — 가이드 3장
4. **사진 저장소 · 백업 확인** — 가이드 4장
5. **Vercel**: 함수 지역 서울 · 환경변수 4개 · 다시 배포 · 접근 보호 — 가이드 5장. 이때 **Production Branch를 `main`으로** 맞춘다(작업 브랜치 커밋이 운영 주소에 먼저 올라간 적이 있음).
6. **연결 확인 10분** — 가이드 6장. 화면 왼쪽 아래 '화면 버전 0.6.1+…'로 배포 버전을 확인한다.
7. **시험 A** (서로 다른 기기 3대, A1~A23) — `docs/FIELD_TEST_EXECUTION.md` 1장. 필수 항목이 모두 통과해야 다음 단계.
8. **시험 C** (안전점검 실제 기록) → **시험 B-1** (실제 업무 사건) → **시험 D** (수기 vs AX).
9. 벤처확인 자료: `docs/VENTURE_CORE_CASE.md` 5장의 실제 증거를 사건 증빙 PDF · CSV · JSON으로 모은다.
