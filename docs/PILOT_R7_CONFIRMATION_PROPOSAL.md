# 취소 일정이 낀 연결의 재판단 — 개선안 (설계안 · 미구현)

작성 2026-11-09 · 상태: **제안** (구현·검증 전) · 관련 규칙: 연쇄위험 엔진 R7 (`src/lib/risk-engine.ts`, chain-risk/1.1.0)

## 1. 현상

같은 직원·같은 날의 두 일정 사이(예정 시작 기준)에 취소된 일정이 있으면, 엔진은 그 연결을
**판단 보류(R7, 이동 기준 불일치)** 로 둔다. 이동시간이 어느 현장에서 출발하는 기준인지 알 수 없기 때문이다.

실증 시스템은 취소 일정을 지우지 않고 '취소' 수정본으로 남기므로(기록 보존), 관리자가 후속 일정의
이동시간을 다시 저장해도 그날 그 연결은 계속 판단 보류로 남는다.

## 2. 결정 (2026-11-09)

1. R7 의 판단 보류 원칙은 유지한다 — 확인되지 않은 이동 기준으로 위험을 판정하지 않는다.
2. 취소가 생기면 관리자에게 후속 현장의 이동 출발지·이동시간 재확인을 안내한다 — **구현됨**
   - 일정 취소 직후 안내 문장: "후속 현장 ○○의 실제 이동 출발지와 이동시간을 다시 확인해 주세요 …"
   - 일정판 상단 '이동 기준 재확인 필요 N건'과 해당 일정 행의 표시 (`cancelledBetween`, `src/lib/pilot/core.ts`)
3. 관리자가 새 연결관계와 이동시간을 **명시적으로 확정한 경우에만** 다시 판정하도록 개선한다 — 이 문서
4. 엔진은 무리하게 바꾸지 않고, 개선이 필요한 단계에서 별도 시험을 더해 기존 113개 시험과 함께 검증한다.

## 3. 개선안 (권장: 엔진 무변경 · 실증 연결부에서 처리)

### 3.1 '연결 확정' 기록 (추가만 하는 기록)

관리자가 후속 일정에서 **[이동 기준 확정]** 을 누르면 다음을 남긴다.

| 항목 | 내용 |
|---|---|
| seq | 변경 기록 공통 번호 (일정 수정본·작업 이벤트와 같은 순서 체계) |
| schedule_id | 후속 일정 |
| from_schedule_id | 관리자가 확정한 이동 출발 일정 (지금 직전 유효 일정) |
| travel_minutes | 확정한 이동시간 |
| cancelled_ids | 관리자가 확인한 사이의 취소 일정들 |
| confirmed_by · recorded_at | 확정한 관리자 · DB 기록시각 |

- 확정은 일정 저장과 같은 방식으로 판단 대기열을 만들어, 확정 전후 위험 판단이 이력으로 남는다.
- 화면은 확정할 값(출발 현장 이름 · 이동시간)을 그대로 보여 주고 한 번 더 확인받는다.

### 3.2 판단 입력 만들기 (`buildPipelineInput`) — 엔진 밖에서만 처리

취소 일정 X 를 엔진 입력에서 **빼는** 조건 (모두 만족할 때만):

1. X 가 걸쳐 있는 후속 연결마다, X 의 취소보다 **나중 번호(seq)** 의 연결 확정이 있다.
2. 그 확정의 출발 일정·이동시간이 **지금 후속 일정의 값과 같다** (확정 뒤 일정·이동시간이 바뀌면 확정은 효력을 잃고 다시 판단 보류).
3. 확정한 출발 일정이 지금도 직전 유효 일정이다.

하나라도 어긋나면 X 를 지금처럼 그대로 넘겨 R7 판단 보류를 유지한다.

- 엔진 파일(`risk-engine.ts`, `state-events.ts`, `priority-engine.ts`)은 바꾸지 않는다.
- 판단 이력에 **연결부 규칙 버전**(예: `pilot-adapter/1.1.0`)과 "확정으로 입력에서 뺀 취소 일정" 목록을
  함께 저장해, 저장된 입력만으로 같은 결과를 다시 계산할 수 있게 한다 (지금의 재계산 확인 방식 유지).

### 3.3 대안 (권장하지 않음): 엔진 R7 에 예외 추가

`travelFromId` 가 직전 유효 일정과 같고 '확정' 표시가 있으면 사이 취소를 무시하는 방식.
판단 규칙 자체가 바뀌므로 규칙 버전을 올리고 기존 판단 결과와의 비교 설명이 필요하다.
실증 기간 중 규칙이 바뀌면 전후 자료 비교가 어려워 권장하지 않는다.

## 4. 검증 계획 (구현 단계에서)

| 구분 | 시험 |
|---|---|
| 기존 | `npm test` 113개 그대로 통과 · 엔진 3개 파일 변경 없음 확인 |
| 단위 | 확정 없음 → 판단 보류 유지 / 확정 후 → 판정 / 확정 뒤 이동시간 변경 → 다시 판단 보류 / 확정 뒤 사이에 새 일정 → 판단 보류 / 데이터 구분 섞임 거부 |
| DB | 확정 기록은 관리자(2단계 인증)만 · 추가만 가능 · 같은 요청 번호 중복 없음 · 판단 대기열 생성 |
| 화면 | 취소 → 안내 → 확정 → 판단 전후 기록에서 '판단 보류 → 판정' 변화 확인 |

## 5. 적용 시점

현장 실증에서 취소가 실제로 얼마나 생기는지 확인한 뒤 적용 여부를 정한다. 그 전까지는 판단 보류와 재확인 안내로 운영한다.
