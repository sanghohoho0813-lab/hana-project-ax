## 1. 처리 흐름

```
실제 작업상태 이벤트 (업무 확인 · 작업개시 · 작업종료 · 완료보고 · 예상 종료 보고)
   │  S1 이벤트 정규화 — 시각 누락·형식 오류·연결 대상 없음은 버림, 중복 정리
   ▼
S2 기대상태 모델 — 단계별 기준시각
   │
   ▼
S3 단계별 편차 = 실제 − 기준 (분)  ← 단계끼리 합산하지 않음
   │
   ▼
S4 엔진 반영 범위 — 작업개시 · 작업종료 · 예상 종료 보고만 일정에 반영
   │
   ▼
R2 선행 예상 종료 결정 (R2-1 · R2-2 · R2-3, 출처와 근거를 남김)
   │
   ▼
R3~R5 연쇄위험 (후속 현장 예상 도착 · 여유 · 위험등급 · 연쇄 전파)
   │
   ▼
P1~P3 관리자 대응 우선순위 (docs/PRIORITY_ENGINE_VERIFICATION.md)
```

전체 흐름 함수: `runStatePipeline({ planned, events, contexts, asOf, assumeDurationKept })` (`src/lib/state-events.ts`).
결과: 채택한 이벤트, 이벤트 문제, 반영된 일정, 단계별 편차, 연쇄위험 결과, 대응 우선순위.

데모 화면은 `opsPipeline()`(`src/lib/ops-calc.ts`)이 데모 일정·업무·보고에서 이벤트를 모아 같은 함수를 부릅니다. 검증 화면과 자동 테스트는 `runFlow()`·`runAbCase()`(`src/lib/state-scenarios.ts`)가 같은 함수를 부릅니다. **편차 분석과 위험 엔진은 예상 종료를 같은 함수 `resolveOwnEnd()`로 계산**하므로 두 결과가 갈라지지 않습니다.

## 2. 기대상태 모델 (S2)

| 단계 | 기준시각 | 기준이 없을 때 | 예상 종료에 반영 |
|---|---|---|---|
| 업무 확인 | 업무 전달 시각 + **120분** | 연결 업무가 없으면 예정 시작 | 반영하지 않음 |
| 작업개시 | 예정 시작 | — | 늦게 시작했고 **작업시간 유지 가정**이 있을 때만 (R2-2) |
| 작업종료 | 예정 종료 | — | 실제 종료가 있으면 그 값 사용 |
| 결과보고 | 업무 완료기한 | 결과보고가 필요 없는 업무는 '해당 없음' | 반영하지 않음 |

- 120분은 기존 '미확인 업무' 알림 규칙(2시간)과 같은 값입니다. 설정값 `EXPECTATION.ackWindowMin`. 실증 데이터로 정한 값이 아닙니다.
- 업무 정보는 일정의 `taskId`로 **정확히 연결되는 경우에만** 씁니다 (`contextsOf`).

### 기준시각에 기대되는 단계 / 실제 단계
편차 결과에는 `expectedPhase`(기준시각에 있어야 할 단계: 확인 대기 · 확인 완료 · 작업 전 · 작업 중 · 작업 종료)와 `actualPhase`(실제 단계)를 함께 남깁니다.

## 3. 이벤트 구조

`StateEvent` (`src/lib/state-events.ts`)

| 필드 | 뜻 |
|---|---|
| `id` | 이벤트 식별자 (같은 id가 두 번 오면 한 번만 씀) |
| `kind` | 업무 확인 · 작업개시 · 작업종료 · 완료보고 · 예상 종료 보고 |
| `siteId` | 대상 일정 |
| `at` | **이벤트 발생시각** `YYYY-MM-DDTHH:MM` (예상 종료 보고는 없을 수 있음) |
| `value` | 예상 종료 보고값 `HH:MM` |
| `source` | 기록 경로 — 업무 확인 버튼 · 작업 시작 버튼 · 현장 보고 · 관리자 입력 · 완료보고 제출 등 |
| `origin` | **데이터 구분** — `데모 데이터` / `데모 세션 입력` / `검증 시나리오` (실사용 데이터와 섞이지 않게 표시) |

### 데모 데이터에서 이벤트를 모으는 규칙 (`eventsFromOps`)
| 이벤트 | 가져오는 곳 | 비고 |
|---|---|---|
| 업무 확인 | 연결 업무의 확인 시각, 없으면 일정 확인 처리 시각 | 데모 데이터 |
| 작업개시 | 일정의 실제 시작 `actualStart` | 작업자 '작업 시작' 버튼(당일 일정만) 또는 일정 화면 '실제 시작 기록' |
| 작업종료 | 일정 상태 '완료' + 실제 종료 `actualEnd` | 완료보고 제출 시 당일 연결 일정에 반영 |
| 완료보고 | 연결 업무의 '완료 보고' 제출 시각 | 데모 데이터 |
| 예상 종료 보고 | 일정의 예상 종료 입력값 | 입력 시각은 기록하지 않으므로 `at` 없음 |

- 데모 데이터의 **'시작 보고'(업무 t4, 09:10)는 작업개시로 쓰지 않습니다.** 그 보고가 어느 일정의 시작인지 정확히 연결되지 않기 때문입니다 (연결 일정 s4는 15:00 시작). 테스트 18번에서 확인합니다.
- 기록에 없는 시각은 만들지 않습니다.

## 4. 편차 계산 (S3)

```
편차(분) = 실제 발생시각 − 기준시각
  > 0  지연
  = 0  정시
  < 0  이름 (작업개시·작업종료) / 기한 내 (업무 확인·결과보고)
아직 발생하지 않음 + 기준시각이 지남 → '미발생 · 기한 경과' (경과 분 표시)
아직 발생하지 않음 + 기준 전          → '기한 전'
진행 중·완료인데 시각 기록 없음      → '시각 기록 없음' (편차 계산 안 함)
```

- **단계별 편차는 합산하지 않습니다.** 예: B현장 업무 확인 20분 지연과 A현장 작업개시 25분 지연은 다른 의미이며 더하지 않습니다.
- 각 단계 결과에 `affectsEnd`(예상 종료 계산에 쓰였는지)와 `meaning`(이 편차가 위험판단에 주는 영향)을 남깁니다.

### 연속 흐름 S1(09:30)의 편차 (`docs/evidence/state-flow-results.json`)
| 현장 | 업무 확인 | 작업개시 | 작업종료 | 결과보고 | 예상 종료 |
|---|---|---|---|---|---|
| A | 기한 내 (−90분) | **지연 25분 · 반영** | 기한 전 | 기한 전 | 11:25 (작업개시 지연 추정) |
| B | **지연 20분 · 반영 안 함** | 기한 전 | 기한 전 | 기한 전 | 12:30 (예정) |
| C | 기한 전 | 기한 전 | 기한 전 | 해당 없음 (연결 업무 없음) | 14:00 (예정) |
| D | 기한 내 (−80분) | 정시 0분 | 기한 전 | 기한 전 | 11:30 (예정) |

## 5. 예상 종료 갱신 규칙 (R2 ~ R2-3, `resolveOwnEnd`)

우선순위 순서대로 처음 맞는 값을 씁니다.

| 순서 | 조건 | 예상 종료 | 출처 표시 | 확정 여부 |
|---|---|---|---|---|
| 1 | 상태 '완료' + 실제 종료 | 실제 종료 | 실제 종료 | 확정 |
| 2 | 예상 종료 보고(현장 보고·관리자 입력) | 보고값 | 현장 보고 / 관리자 입력 | 확정 |
| 3 | R2-2: 실제 시작이 늦음 **그리고** 작업시간 유지 가정 명시 | 실제 시작 + 예정 작업시간 | 작업개시 지연 추정 | 확정 (가정 표시) |
| 3 | R2-1: 진행 중 + 기준시각이 예정 종료를 지남 + 보고 없음 | 최소 기준시각 | 추정 규칙 | 확정 |
| — | (3의 후보가 둘 다 있으면 늦은 값) | | | |
| 4 | R2-3: 늦게 시작했는데 가정 없음 | 예정 종료 | 예정 | **미확정** |
| 4 | R2-3: 상태 '예정' + 예정 시작이 지남 + 시작 기록 없음 | 예정 종료 | 예정 | **미확정** |
| 5 | 그 밖 | 예정 종료 | 예정 | 확정 |

- **일찍 시작해도 예상 종료를 앞당기지 않습니다** (08:50 시작 → 종료 11:00 그대로).
- R2-2는 **규칙 기반 추정**입니다. 근거 문장에 가정을 그대로 남깁니다. 예: `실제 시작 09:25 (25분 늦음) + 예정 작업시간 120분 — 가정: 늦게 시작해도 작업시간 유지`.
- 운영 화면과 검증 화면은 이 가정을 켜고(`OPS_ASSUMPTIONS.assumeDurationKept = true`, `FLOW_ASSUME_DURATION_KEPT = true`) 화면에 문구를 표시합니다. 엔진 기본값은 **꺼짐**입니다.
- 미확정이면 판단 근거에 "선행 현장 예상 종료가 확정되지 않아 예정 종료 기준으로 계산했습니다 — 실제 지연은 더 클 수 있습니다"를 붙이고, 권장 확인에 '선행 현장 종료 예상시각 확인'을 넣습니다.
- 예정 상태 일정에 실제 시작이 기록되면 상태를 '진행 중'으로 봅니다.

### A → B 검증 예시 1~4 (`AB_CASES`, 기대값은 시나리오에 따로 적어 둠)
| # | 입력 | A 예상 종료 (출처) | B 예상 도착 | 여유 | 등급 | 우선순위 |
|---|---|---|---|---|---|---|
| 1 | A 09:00 정시 시작 | 11:00 (예정) | 11:30 | 10분 | 없음 | 없음 |
| 2 | A 09:25 시작 | 11:25 (작업개시 지연 추정) | 11:55 | −15분 | 높음 | 1. B현장 작업지연 위험 65점 |
| 3 | + 현장 보고 예상 종료 11:10 | 11:10 (현장 보고) | 11:40 | 0분 | 주의 | 없음 |
| 4 | + 관리자가 B를 12:10 시작으로 조정 | 11:10 (현장 보고) | 11:40 | 30분 | 없음 | 없음 |

공통: A 09:00~11:00, A→B 이동 30분(입력값), B 11:40~12:30. 네 경우 모두 기대값과 일치 (테스트 9번).

## 6. 예외 처리

| 상황 | 처리 | 기록되는 문제 |
|---|---|---|
| 발생시각이 없는 작업개시·작업종료·업무 확인·완료보고 | 쓰지 않음. **시각을 만들어 넣지 않음** | 이벤트 시각 누락 |
| 발생시각 형식 오류 (`09:7` 등) | 쓰지 않음 | 이벤트 시각 형식 오류 |
| 없는 일정을 가리키는 이벤트 | 쓰지 않음 | 연결 대상 없음 |
| 같은 id가 두 번 | 한 번만 씀 | 중복 이벤트 |
| 같은 일정·같은 단계가 여러 번 | 가장 이른 기록 사용 (예상 종료 보고는 가장 늦은 보고). 입력 순서와 무관 | 중복 이벤트 |
| 예상 종료 보고값을 읽을 수 없음 | 쓰지 않음 | 보고값 오류 |
| 이벤트 날짜가 일정 날짜와 다름 | 쓰지 않음 | 날짜 불일치 |
| 작업종료가 작업개시보다 빠름 | 종료를 쓰지 않음 | 시간 역행 |
| 일정 자체의 시각·날짜 오류, 이동시간 누락 | 위험 엔진 R7 — 판단 보류 | 위험 엔진의 데이터 문제 |

## 9. 한계

- 이벤트는 데모 화면의 버튼·입력과 데모 데이터에서 옵니다. 실제 현장 단말·서버에서 수집하는 경로는 없습니다. 기록은 **브라우저 메모리**에만 있고 새로고침하면 사라집니다.
- 예상 종료 보고의 입력 시각은 기록하지 않습니다 (기존 데이터에 없는 시각을 만들지 않음).
- R2-2의 '작업시간 유지'는 **가정**입니다. 실제 작업시간 분포로 검증하지 않았습니다.
- 확인 기준 120분은 기존 알림 규칙 값을 따른 설정값이며 실증으로 정한 값이 아닙니다.
- 작업자 '작업 시작' 버튼은 데모 기준시각(10:40)을 실제 시작으로 기록합니다. 실제 현재시각 처리(운영모드)는 구현되지 않았습니다.
- 역할 전환은 데모 기능이며 실제 서버 인증이 아닙니다. 누가 이벤트를 입력했는지에 대한 인증·위변조 방지는 없습니다.
- 시험 데이터는 가상 시나리오와 데모 데이터입니다. 실제 운영데이터로 검증하지 않았습니다.
