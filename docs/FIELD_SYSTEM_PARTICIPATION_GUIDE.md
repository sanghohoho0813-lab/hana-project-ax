# 현장 참여시험 방법 및 증빙자료 수집 가이드 (현장 실사용 AX 시스템 0.3.0)

대상 기술: **복수 현장 업무 위험관리 AX 시스템** — 현장 문제가 후속 현장 일정에 주는 연쇄위험을 더 빨리, 더 정확히 판단하는지 확인한다.
전제: 운영 Supabase · Vercel 설정이 끝나 실제 주소로 접속할 수 있어야 한다 (`docs/FIELD_SYSTEM_DEPLOYMENT.md`). **지금은 아직 시작 전이다.**

---

## 1. 원칙 (모든 시험에 공통)

1. **자료를 섞지 않는다.**
   - `실제 업무`: 오늘 실제로 일어난 일을 그때 입력한 것.
   - `현장정보 재현`: 지난 업무를 업무일지·통화기록·진술로 다시 입력한 것.
   - `가상 시나리오`: 연습·시험용으로 만든 상황.
   - 기록마다 이 구분이 붙고, 성과 측정 화면도 따로 집계한다.
2. **측정하지 않은 값은 비워 둔다.** 시각을 모르면 '모름'을 고른다. 기억으로 넣은 값은 '기억에 의한 추정'으로 표시되어 통계에서 빠진다.
3. **개선율을 만들지 않는다.** 수기와 AX를 같은 조건에서 모두 쟀을 때만 '이번 측정값'으로 비교한다. 유의성 검정이 아니며, 표본이 적다는 것을 함께 적는다.
4. **누가 입력했는지 남긴다.** 현장기사가 직접 입력하면 '본인 입력'이다. 관리자가 전화로 듣고 대신 입력하면 '대리 입력(정보 제공: 현장기사)'으로 남는다.
5. **안전이 먼저다.** 안전 위험을 보면 시험보다 먼저 작업을 멈추고 본사에 전화한다. 프로그램 기록은 그다음이다.
6. **고치지 않고 덧붙인다.** 잘못 누른 기록은 지우지 않는다. 정정이나 무효 기록을 더한다. 사건은 관리자가 '무효 처리'한다.

## 2. 준비

| 준비물 | 내용 | 확인 |
|---|---|---|
| 관리자 PC | 1대 이상 (Chrome 또는 Edge 최신), 인증 앱이 깔린 휴대폰 (TOTP 2단계 인증) | ☐ |
| 현장기사 휴대폰 | **서로 다른 휴대폰 2대 이상** (가능하면 iPhone 1 + Android 1, 이동통신망 사용) | ☐ |
| 계정 | 관리자 1~2명, 현장기사 2명 이상 — 초대 메일로 비밀번호 설정 → 관리자가 계정 관리에서 활성화 | ☐ |
| 일정 | 관리자가 일정판에 그날 일정 등록 (기사 · 현장 · 예정 시작·종료 · 직전 현장에서 이동시간) | ☐ |
| 시험 일지 | 9장 양식 (종이 또는 표 파일) — 기기·시각·결과를 그 자리에서 적는다 | ☐ |
| 안전점검 항목 | 회사 안전기준으로 확정 (지금 8개 항목은 초안) | ☐ |
| 촬영 안내 | 얼굴 · 차량번호 · 고객 서류가 찍히지 않게 (`FIELD_SYSTEM_DEPLOYMENT.md` 3-5) | ☐ |

**기기 정보 기록** (시험 일지 첫 장): 기기 이름, 운영체제 버전, 브라우저, 통신(와이파이/LTE/5G), 사용자(관리자/기사 A/기사 B).

## 3. 시험 A — 실제 기기 연동 (배포 직후, 30~40분, `가상 시나리오`)

다른 시험보다 먼저 한다. **통과하기 전에는 시험 B~D를 시작하지 않는다.**

| # | 하는 일 | 확인할 것 | 기록 |
|---|---|---|---|
| A1 | 세 기기에서 각자 로그인 (관리자는 2단계 인증) | 화면 띠에 `실증 DB` 표시 · 기사는 본인 일정만 보임 | 시각 · 통과/실패 |
| A2 | 기사 A 휴대폰: 작업 시작 → 현장 문제 보고 (사진 1장 촬영 · +1시간) | 보고 화면이 '보고됨'으로 바뀜 · 사진 미리보기 | 기사 A가 누른 시각 |
| A3 | 관리자 PC: 새로 고침 하지 않고 기다림 | 10초 안팎에 사건이 맨 위에 나타남 · 우선 확인 이유에 후속 현장 위험(계산값) | 나타난 시각 → **A2와의 차이(초)** |
| A4 | 관리자: 사진 열기 | 실제 찍은 사진이 열림 · '촬영정보 제거' 표시 | 통과/실패 |
| A5 | 관리자: 접수 → 담당자 배정 → 지원 결정 → 현장 전달 | 처리 흐름에 순서대로 쌓임 | — |
| A6 | 기사 A 휴대폰: 기다림 | 15초 안팎에 현장 전달 내용이 보임 | 보인 시각 → 차이(초) |
| A7 | 관리자: 일정 조정 (B현장 시작 늦춤) | 재판단 전·후 표시 (해소/유지/새 위험) | 판단 번호 |
| A8 | 기사 B 휴대폰 | A의 일정·사건·사진이 **보이지 않음** · 관리자 주소를 직접 쳐도 들어가지 못함 | 통과/실패 |
| A9 | 기사 A: 비행기 모드로 보고 → '다시 보내기' → 비행기 모드 끄고 다시 보내기 | 사건이 **1건만** 생김 | 사건번호 |
| A10 | 기사 A: 해결 보고 → 관리자: 해결 확인 | '끝난 사건'으로 이동 · 증빙 화면 인쇄(PDF) | 사건번호 |

**실패하면**: 그 자리에서 성과 측정 화면의 '의견·오류·개선 입력'에 **오류**로 남긴다. 기기·시각·화면 사진을 함께 적는다. 고친 뒤 같은 시험을 다시 하고, '개선 반영'으로 원래 오류와 연결한다.

## 4. 시험 B — 현장 문제 → 해결 전체 흐름 (`실제 업무` 또는 `현장정보 재현`)

### B-1. 실제 업무 (가장 강한 증거)

1. 현장기사는 평소처럼 일한다. 예상과 다른 상황이 생기면 **그 자리에서** '현장 문제 보고 · 지원 요청'을 누른다.
   - 발견시각: 지금 / 10분 전 / 30분 전 / 1시간 전 / 모름. 보고 시각은 버튼을 누른 시각이 자동으로 들어간다.
   - 변경 예상 종료를 모르면 **'아직 모름'**. 프로그램은 이 보고를 위험 판단에 넣지 않고 '예상 종료 미확인'으로 띄운다.
2. 관리자는 평소처럼 처리하되, **실제로 한 일만** 버튼으로 남긴다 (접수 · 배정 · 지원 결정 · 현장 전달 · 일정 조정).
3. 해결되면 기사가 해결 보고 → 관리자가 해결 확인.
4. 전화로만 들은 내용은 관리자가 '대리 입력'으로 남긴다 (정보 출처: 전화).

### B-2. 현장정보 재현 (지난 사례)

1. 지난 사례의 원자료를 모은다: 업무일지, 일정표, 통화기록, 메신저 대화 (원본은 회사가 보관하고 프로그램에는 이름만 적는다).
2. 관리자가 그날 일정을 검증 시나리오 날짜로 다시 등록한다.
3. 보고와 조치를 **사후 입력**으로 넣고 시각 근거를 고른다: 원자료 기록 / 현장 직원 진술 / 기억에 의한 추정 / 모름.
4. 자료 구분은 반드시 **'현장정보 재현'** 으로 고른다.

### B-3. 사건마다 확인할 것 (증빙 화면에서)

- 시각: 발견 · 보고 · 서버 기록이 따로 있는가.
- 사진: 지문(SHA-256) · 보관 기한이 있는가.
- 조치: 순서대로 쌓였고 중복이 없는가.
- 엔진: 예상 종료 입력, 후속 현장 도착(계산값), 위험 등급 전·후가 있는가.
- 측정 1~4: 값과 품질(실측 · 원자료 · 진술 · 추정)이 있는가.

## 5. 시험 C — 안전점검 (`실제 업무` 권장)

1. 기사는 작업 전에 '시작 전 점검'을 한다. 필수 3항목을 답하고, 착용 사진을 1장 이상 찍어 제출한다. 작업 중과 마친 뒤에도 같은 방식으로 점검한다.
2. **'미흡'이 있으면 화면 안내대로 작업을 멈추고 본사에 전화한다.**
3. 관리자는 안전점검 화면에서 사진을 **직접 보고** 판단한다.
   - 이상이 없으면 '적합(육안 확인)'을 누른다.
   - 문제가 있으면 '보완 요청'과 요청 내용을 남긴다.
   - 기사가 보완 사진을 제출하면 '조치 완료'를 누른다.
4. 확인할 것:
   - 사진만으로 자동 적합이 되지 않는가.
   - 미흡 항목이 있으면 적합 버튼이 막히는가.
   - 보완 이력이 남는가.
   - 작업 전 점검이 없는 일정이 관리자 화면에 보이는가.

## 6. 시험 D — 수기 방식 vs AX 방식 (측정 7)

같은 상황에서 기존 방식(종이 일정표 · 전화 메모)과 AX 시스템으로 위험을 파악하는 시간과 정확도를 잰다.

| 단계 | 방법 |
|---|---|
| 시나리오 준비 | 진행자(참가자 아님)가 시나리오와 **정답표**(위험한 연결 · 영향받는 현장)를 미리 만든다. 실제 사례 재현이면 '현장정보 재현', 만든 상황이면 '가상 시나리오' |
| 짝 맞추기 | 같은 시나리오의 수기 측정과 AX 측정에 같은 '대응 묶음' 이름을 붙인다 (예: `I3-1`) |
| 순서 | 학습 효과를 줄이려고 참가자마다 순서를 바꾼다 (참가자 1: 수기 → AX, 참가자 2: AX → 수기). 같은 참가자에게는 비슷한 난이도의 다른 시나리오를 쓴다 |
| 측정 | 성과 측정 화면의 **앱 측정기**: 시작 → 위험 파악 끝 → (조치 전달) → 재판단 끝. 측정기를 못 쓰면 스톱워치나 기록지 값을 넣고 측정 방법을 그대로 고른다 |
| 정확도 | 정확히 찾은 위험 / 정답 위험 수 · 놓친 위험 · 잘못 판단한 위험 — 진행자가 정답표로 채점 |
| 값의 근거 | 시험 실측 / 과거 기록 / 기억 추정 (기억 추정은 비교에서 빠짐) |
| 잘못 잰 측정 | 지우지 않고 '무효'와 사유를 남긴다 |

결과는 성과 측정 화면에 '이번 측정값 (수기 n, AX n) · 중앙값 차이 · 통계적 유의성 검정 아님'으로만 나온다. 보고서에는 참가자 수와 측정 횟수를 함께 적는다.

## 7. 의견 · 오류 · 개선 이력 (측정 8 · 9)

| 누가 | 어디서 | 종류 |
|---|---|---|
| 현장기사 | 휴대폰 화면 아래 '프로그램 의견 · 오류 보내기' | 현장기사 의견 · 오류 (본인 입력) |
| 관리자 | 성과 측정 → 의견·오류·개선 입력 | 관리자 의견 · 오류 · 개선 요청 · 개선 반영 |

- 들은 의견을 대신 적을 때는 말한 사람과 '본인 확인 여부'를 고른다.
- 고친 뒤에는 **'개선 반영'** 을 남긴다. 원래 의견이나 오류를 고르고, 바뀐 날짜와 프로그램 버전을 함께 적는다. 버전 칸에는 지금 버전(`0.3.0+커밋`)이 미리 들어가 있다. 고치기 전후 버전이 증빙이 된다.
- 고친 기능은 같은 시험을 다시 해서 결과를 남긴다 (재시험).

## 8. 증빙자료 수집 — 사건번호 단위

| 자료 | 어디서 | 담기는 것 | 파일 이름 (권장) |
|---|---|---|---|
| **사건 증빙 PDF** | 현장 문제·지원 → 사건 → 인쇄 → PDF로 저장 | 사건 · 참가자 · 출처 · 시각 4종 · 사진 · 조치 이력 · 엔진 입력 · 판단 전후 · 측정 1~6 | `사건번호_증빙_출력일.pdf` |
| 사건 JSON | 같은 화면 'JSON 내려받기' | 원자료 전체 (사진은 지문 · 크기 · 경로만, 서명 주소 없음) | `사건번호.json` |
| 사건 CSV | 같은 화면 'CSV 내려받기' | 사건 1행(측정 1~4 분 · 품질 포함) + 조치 단계별 1행 (실제 시각 · 근거 · 서버 기록시각 · 입력자 · 버전 · 엔진 기록 번호) | `사건번호.csv` |
| 위험 판단 기록 | 기록·판단 이력 → 판단 번호 → 인쇄 / 원본 JSON | 판단 입력 · 결과 · 바뀐 연결 · 규칙 버전 · 서명 지문 | `판단번호.pdf/json` |
| 측정 CSV 3종 | 성과 측정 → CSV (사건 측정 · 수기 vs AX · 의견·오류·개선) | 기간 · 자료 구분별 | `측정_종류_기간.csv` |
| 시험 일지 | 9장 양식 | 기기 · 시각 · 결과 · 실패 내용 | `시험일지_날짜.pdf` |
| 원자료 사본 | 회사 보관 (업무일지 · 통화기록 등) | 현장정보 재현의 근거 | 원자료 이름을 프로그램 기록에 적어 연결 |

**보관 방법**
- 시험이 끝난 날 사건 증빙 PDF와 JSON을 내려받아 날짜별 폴더에 둔다.
- 측정 CSV는 주 단위로 받는다.
- 사진 원본은 저장소에만 둔다. PDF에 들어간 사진은 인쇄본이고, JSON의 지문으로 같은 파일인지 확인한다.
- 증빙에 개인정보가 보이면(얼굴 · 차량번호 등) 외부 제출 전에 가린다. 원본 사진은 삭제기준에 따라 관리자가 처리한다.

**보고서에 쓰는 문장 원칙**
- "실제 업무 N건 · 현장정보 재현 N건 · 가상 시나리오 N건"처럼 구분과 건수를 먼저 쓴다.
- 소요시간은 '중앙값 (범위, n, 품질)'로 쓰고, 추정값은 따로 쓴다.
- 엔진 결과는 '계산값'이라고 쓰고, 입력값과 구분한다.
- 측정하지 않은 효과(절감시간, 개선율, 비용)는 쓰지 않는다. 기대 효과를 쓰려면 '예상'이라고 따로 표시한다.

## 9. 시험 일지 양식

## 10. 하지 말 것

- 시험이나 연습 기록을 `실제 업무`로 입력하지 않는다.
- 모르는 시각을 그럴듯하게 채우지 않는다. 모르면 '모름'을 고른다.
- 측정하지 않은 개선율이나 절감효과를 보고서에 쓰지 않는다.
- 사진이 있다는 것만으로 안전 '적합'을 누르지 않는다. 사진을 직접 보고 판단한다.
- 기존 브라우저 저장판(0.2.0)의 가상 시험 기록을 이 DB에 옮기지 않는다.
- 로컬 개발용 시험 결과를 현장 실증 결과로 쓰지 않는다 (`FIELD_SYSTEM_0.3.md` 9장은 로컬 자체 시험이다).
