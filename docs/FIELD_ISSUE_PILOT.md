# 현장 문제 보고 · 지원 요청 — 인터뷰 기반 실증 기능 보강 (프로그램 0.2.0)

대상: 실증 전용 간소화 버전(브라우저 저장판) — 새 시스템을 만들지 않고, 기존 「복수 현장 업무 위험관리 AX 시스템」 엔진에 실제 현장 문제를 연결하는 최소 기능만 더했다.
엔진(`src/lib/risk-engine.ts` · `state-events.ts` · `priority-engine.ts`), 비교시험(`trial/`), 기존 테스트(`tests/`), 특허 관련 코드는 바꾸지 않았다.

> 기록은 이 브라우저(localStorage)에만 저장된다. 다른 기기와 공유되지 않는다.
> PC+Mobile 동시 보기는 **같은 브라우저 안의 시험 화면**이며, 현장과 본사 사이 실시간 연동이 아니다.

## 1. 인터뷰 근거 (2026-11-13 · 구본석 이사)

확인된 사실 (기술기획의 근거로만 사용)

1. 현장기사가 기술적 문제를 혼자 해결하려다가 본사 지원 요청이 늦어지는 경우가 있다.
2. 분해·설치를 시작한 뒤 예상과 다른 상황이 확인되는 경우가 있다.
3. 추가 장비 또는 숙련 기술자가 필요한 경우가 있다.
4. 현장에서는 "문제를 일찍 알렸다면 본사가 더 빨리 지원할 수 있었다"는 의견이 있었다.
5. 일부 지연으로 다음 현장을 계획한 날 방문하지 못한 사례가 있었다.
6. 작업 전·중·후 안전장비 착용을 사진으로 확인하면 좋겠다는 의견이 있었다.

**확인되지 않은 것 (만들지 않음)**
- 후속 일정 지연이 자주 발생한다는 것
- 고객 불만이나 매출 손실이 발생했다는 것
- 실제 발생빈도와 개선효과

프로그램·문서·보고서 어디에도 발생빈도나 개선효과를 적지 않았다. 시험 시나리오의 시각·작업시간·이동시간은 모두 **시험용 가정값**이다.

## 2. 인터뷰 문제 → 구현 기능 대응표

| 인터뷰에서 확인한 문제 | 구현한 기능 | 화면 | 남는 데이터 |
|---|---|---|---|
| ① 기사가 혼자 해결하다 지원 요청이 늦어짐 | **현장 문제 보고 · 지원 요청** 버튼. 문제 발견시각과 본사 보고 시각을 따로 받는다 | 현장기사 모바일 카드 | 발견→첫 보고 소요시간과 시각 근거 |
| ② 분해·설치 시작 후 예상과 다른 상황 | 문제 유형 '예상과 다른 현장상황', 진행상황 '분해·설치 시작 후' 버튼 | 현장기사 모바일 | 유형·진행상황 |
| ③ 추가 장비·숙련 기술자 필요 | 유형 '추가 장비 필요'·'기술 지원 필요', 지원 요청 버튼(원격 기술 지원·숙련 기술자·추가 장비·일정 조정) | 현장기사 모바일 | 요청 항목·요청 원문 |
| ④ 일찍 알렸다면 본사 지원이 빨랐을 것 | 관리자의 **접수 · 지원 조치 결정 · 일정 조정 · 해결 여부** 기록. 각 시각과 근거를 따로 받는다 | 관리자(PC) 현장 문제 패널 | 보고→접수, 보고→지원 결정, 지원 요청→해결 소요시간 |
| ⑤ 지연으로 다음 현장 방문 불가 | 변경 예상 종료가 확인되면 기존 '예상 종료 보고'로 엔진에 전달해 **후속 현장 위험을 계산**한다. 관리자 일정 조정 뒤 **재판단** | 관리자 패널 '처리 흐름', 판단 전→후 | 조치 전후 위험 등급·연결 수·최대 지연(분, 계산값) |
| ⑥ 안전장비 사진 확인 | **이번 범위에서 제외.** 후속 요구사항으로만 문서화(아래 7장) | — | — |
| (공통) 출처·입력자 구분 | 기존 '입력 출처'를 그대로 사용: 입력자, 정보 제공자, 자료 출처, 원자료, 입력 화면, 프로그램 버전 | 모든 입력 | 기록마다 저장 |

현장 문제 보고 입력은 버튼만으로 끝난다. 유형 → 진행상황 → 지원 요청 → 변경 예상 종료(+30분 / +1시간 / +2시간 / 직접 입력 / 아직 모름) → 발견시각 → 보고 보내기. 화면 시험에서는 버튼 6번에 시각 입력 2칸이었다. 실제 업무 세트에서는 '지금'과 '10분 전 / 30분 전 / 1시간 전' 버튼을 쓰고, 보고 시각은 버튼을 누른 시각이 된다.

## 3. 엔진 연결 방식 (엔진 변경 없음)

```
현장 문제 발견 (입력값)
  → 문제 보고 · 지원 요청 (입력값 — 별도 '현장 문제' 기록. 판단을 만들지 않음)
  → 예상 종료시간 변경 (입력값 — 확인된 경우에만 기존 '예상 종료 보고' 기록 1건으로 엔진에 전달)
  → 후속 현장 위험 계산 (계산값 — 기존 엔진이 판단 전·후를 계산)
  → 관리자 조치 (입력값 — 접수·지원 결정·일정 조정·해결 여부)
  → 재판단 (계산값 — 일정 조정은 기존 '일정 수정' 기록으로 저장되고 그 판단 전·후가 재판단)
```

- 문제 보고 자체는 위험으로 판정하지 않는다. 예상 종료를 모르면 문제 기록만 남는다. 엔진 입력과 판단 기록은 늘지 않는다(단위시험·화면시험으로 확인).
- 엔진에 넘기는 값은 '예상 종료 시각'과 '보고 시각(근거 포함)'뿐이다. 보고 시각을 모르면 기존 규칙대로 엔진이 그 기록을 쓰지 않는다(이벤트 시각 누락).
- 관리자 일정 조정은 시스템이 하지 않는다. 관리자가 정한 값만 저장한다.
- 잘못 입력한 문제를 무효 처리하면, 그 문제에서 엔진에 넘긴 예상 종료 기록도 '기록 무효'가 된다. 이미 바꾼 일정은 되돌리지 않는다(실제 조치였으므로).
- 저장된 판단을 다시 계산해도 같은 결과가 나온다(백업 검사와 단위시험으로 확인).

## 4. 시험 방법

### 4-1. 시험 방식 — 결과를 섞지 않는다

세트마다, 그리고 비교시험 측정마다 시험 방식을 기록한다. 바꾸면 변경 이력이 남는다.

| 시험 방식 | 뜻 |
|---|---|
| 구본석 이사 직접 수행 | 참여자가 직접 화면을 눌러 시험 |
| 컨설턴트 진행 | 컨설턴트가 입력·진행 (참여자 미수행) |
| 과거 현장정보 재현시험 | 지난 현장 정보를 원자료·진술로 다시 입력 |

### 4-2. 데이터 구분과 소요시간 품질

| 데이터 구분 | 보고서 위치 | 소요시간 품질 |
|---|---|---|
| 실제 업무 (오늘, 버튼 누른 시각) | ③-1 **실측 결과** | 두 시각이 모두 버튼 시각이면 '실측'. 기사가 말한 발견시각이면 '진술' |
| 사후 재현 (지난 현장정보) | ③-2 **현장정보 재현 결과** | 업무일지·메신저 시각은 '원자료', 말한 시각은 '진술', **기억에 의한 값은 '추정'** |
| 가상 시나리오 | ③-3 **가상 시나리오 결과** | '가상' (실제 효과 아님) |
| 사람이 쓴 예상 | ⑥ **향후 예상 효과** | 측정값 아님 |

- 소요시간 품질은 두 시각 근거 중 약한 쪽을 따른다.
- '추정' 값은 통계와 비교에 넣지 않고 따로 적는다.
- 기존 방식(수기) 소요시간도 같은 원칙을 따른다. 비교시험 측정의 '소요시간 근거'를 '시험 실측 / 과거 기록 / 기억 추정' 중 하나로 고른다. 기억 추정은 비교 통계에서 뺀다.

### 4-3. 시험 시나리오 (가상 · 시험용 가정값)

'현장 실증 → 현장 문제 시나리오'에서 불러온다. 일정 A·B·C와 A현장 작업 시작(09:00)까지만 들어간다. 문제 보고와 관리자 조치는 참여자가 시나리오 카드대로 화면에서 직접 입력한다.

공통 일정: A 09:00~10:00 · B 10:30~12:00 (A에서 이동 20분) · C 13:00~14:30 (B에서 이동 30분)

| 시나리오 | 카드 (입력할 상황) | 정답 (손 계산 = 엔진 결과, 단위시험으로 확인) |
|---|---|---|
| I1 정상 작업 | 10:00 A 작업 종료, 문제 없음 | 위험 0 (A→B 여유 10분, B→C 여유 30분) |
| I2 조기 지원 요청 | 09:20 발견 → 09:25 보고 (예상 종료 10:40) → 09:27 접수 → 09:30 지원 결정, B 11:00~12:30 조정 → 10:40 해결 | 보고 전 0 → **보고 후 1** (A→B 30분 늦음 매우 높음, B→C 주의) → 조정 후 0 (A→B 주의, B→C 주의) |
| I3 지원 요청 지연 | 09:20 발견 → 10:20 보고 (예상 종료 11:10) → 10:22 접수 → 10:30 결정, B 11:30~13:00 → 10:32 C 13:30~15:00 → 11:10 해결 | 보고 직전 1 (엔진 추정 규칙*) → **보고 후 2** (A→B 60분, B→C 30분 늦음) → B 조정 후 1 → C 조정 후 0 |

\* I3 '보고 직전 1건'은 엔진 규칙에서 나온다. 기준시각 10:20에 A가 예정 종료(10:00)를 지났는데 종료 보고가 없으면, 엔진은 'A는 최소 10:20까지 작업'으로 보고 A→B를 10분 늦음(높음)으로 판단한다. 처음 손으로 계산할 때 놓치기 쉬운 결과라 정답표에 그대로 적었다. 시험에서 예상과 다르면 '예상과 다름'으로 남긴다.

### 4-4. 1회 시험 순서 (PC+Mobile 보기 권장)

1. 상단 '입력자'를 고른다. 현장 실증 → 관리자 시점 → '현장 문제 시나리오' → I1·I2·I3 중 하나 → **시험 방식**을 고른다.
2. 진행요원이 시나리오 카드를 읽어 준다. 비교시험을 함께 잴 때는 '전후 비교시험'의 앱 측정기를 '1부 시작'으로 둔다.
3. 모바일(현장기사 시점) A현장 카드 → **현장 문제 보고 · 지원 요청** → 카드의 값을 입력 → 보고 보내기.
4. PC 관리자 화면의 '현장 문제 · 지원 요청'에서 후속 현장 위험(판단 전→후)을 확인한다. 위험을 찾으면 측정기 '1부 끝'.
5. 접수 → 지원 결정 → 일정 조정(조치한 시각 입력) → 재판단을 확인한다. 측정기는 '조치 전달' / '2부 끝'.
6. 모바일에서 해결 여부를 기록한다. '처리 흐름'에서 입력값과 계산값을 확인한다.
7. 세트 정보의 **'이번 회차 결과가 예상과 같았나요?'**에 예상대로 / 예상과 다름(어떻게) / 판단 못 함을 기록한다.
8. 기존 방식(수기)은 같은 카드를 종이·전화 방식으로 풀어 '전후 비교시험'에 수기 측정으로 넣는다. 시나리오 I1~I3을 고르면 정답표 값 버튼이 생긴다.
9. 참여자 의견은 '문제·피드백'에 **관련 세트**를 골라 원문 그대로 적는다. 의견 때문에 요구사항이나 프로그램이 바뀌면 '요구사항·프로그램 변경 기록'에 날짜, 내용, 버전을 남긴다.
10. '실증 기록·내보내기' → 세트 표의 **증거 기록**을 인쇄(PDF)하고 JSON 백업을 받는다.

반복할 때는 '같은 시나리오로 반복'을 누른다. 시작 상태부터 새 회차가 만들어진다.

### 4-5. 실제 현장정보 재현

1. '새 세트'에서 데이터 구분 '사후 재현', 시험 방식 '과거 현장정보 재현시험'을 고른다. 원자료(업무일지·메신저 이름)를 적는다.
2. 일정을 원자료대로 넣는다. 현장기사 시점에서 '현장 문제 보고'를 누르고 발견·보고 시각을 넣는다.
3. 각 시각에는 근거를 고른다. 원자료에 있으면 '원자료 기록', 들은 시각이면 '정보 제공자 진술', 기억이면 '기억에 의한 추정'. 모르면 '모름'으로 비워 두고 추정해 채우지 않는다.
4. 관리자 조치도 실제로 한 시각과 근거로 넣는다.

## 10. 한계

- 모든 결과는 로컬 자체시험 결과다. **실제 현장 실증(구본석 이사 직접 수행, 실제 업무 세트)은 아직 하지 않았다.**
- 시나리오의 시각·작업시간·이동시간은 가정값이다. 결과는 실제 발생빈도나 실제 개선효과가 아니다.
- 한 브라우저 저장이라 다른 기기와 공유되지 않는다. PC+Mobile 보기는 현장↔본사 실시간 연동이 아니다.
- 위험 등급과 지연(분)은 규칙 기반 계산값(관리자 판단 지원)이며 확률이 아니다.
