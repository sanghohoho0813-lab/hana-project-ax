## 1. 기술의 목적과 해결 대상

정보통신·전기공사처럼 한 작업자가 하루에 여러 현장을 차례로 맡는 업종에서는, 앞 현장이 늦게 끝나면 다음 현장 도착이 늦어집니다. 기존 일정표는 **예정 시간**만 보기 때문에, 다음 현장이 아직 시작 전이면 '정상'으로 보입니다.

이번 구현은 다음 문제를 해결 대상으로 합니다.

1. 선행 현장의 **예상 종료**(현장 보고·관리자 입력·명시된 추정규칙)와 **현장 간 이동 필요시간**을 이어서, 아직 시작하지 않은 후속 현장의 **예상 도착·지연 위험**을 미리 계산한다.
2. 지연이 B현장에서 끝나지 않고 C현장, D현장으로 이어지는 **연쇄 영향**을 계산한다.
3. 판단 근거(입력값·계산식·적용 규칙)를 관리자와 심사자가 그대로 확인할 수 있게 보여준다.
4. 취소·중복·시간 오류·이동시간 누락 같은 데이터 문제를 **오판정 없이** '판단 보류'로 구분한다.
5. 일정·담당자는 자동으로 바꾸지 않고, 관리자가 확인할 항목만 제시한다.

## 3. 핵심 처리구조

```
일정 데이터 (같은 작업자·같은 날짜)
   │  R7 데이터 확인: 중복 제거 · 취소/날짜·시각 오류 제외 (위치는 기억)
   ▼
R1 연결: 예정 시작 순으로 정렬해 인접 일정끼리 연결 (선행 → 후속)
   │
   ▼
R2 선행 현장 종료시각 결정 + 출처 기록
   실제 종료 > 예상 종료(현장 보고 · 관리자 입력) > R2-1 추정 규칙 > 예정 종료
   │
   ▼
R3 예상 도착 = 선행 예상 종료 + 이동 필요시간 (출처: 입력값 · 데모 가정값)
   │
   ▼
R4 여유 = 후속 예정 시작 − 예상 도착  →  위험등급 · 원인 · 권장 확인
   │
   ▼
R5 연쇄 전파: 후속 예상 시작 = max(예정 시작, 예상 도착), 작업시간 유지 → 예상 종료 재계산
   │      → 다음 연결의 '선행 예상 종료'로 사용 (출처: 연쇄 계산)
   ▼
결과: 연결별 판정(RiskLink) · 일정별 예상 시간(ProjectedSite) · 데이터 문제 · 제외 목록
   │
   ├─ 통합일정 화면 '연쇄위험 판단 근거' 패널
   ├─ 첫 화면·알림 '연쇄 지연 위험' (예정값만으로 걸리는 건은 기존 '일정 충돌'로 이미 표시되므로 중복 제외)
   └─ 판단 이력 (변경 전후 diffRisk)
```

엔진은 순수 함수 `evaluateChainRisk(inputs, { asOf })` 하나입니다. 다른 모듈을 가져오지 않고, 현재 시각을 스스로 읽지 않으며(기준시각은 인자로만 받음), 입력 객체를 바꾸지 않습니다.

## 4. 입력 데이터

엔진 입력 `SiteInput` (`src/lib/risk-engine.ts`). 데모 화면에서는 `ScheduleItem` 을 `toSiteInput()`(`src/lib/ops-calc.ts`)으로 바꿔 넣습니다.

| 필드 | 뜻 | 비고 |
|---|---|---|
| `id`, `title`, `region` | 일정 식별·표시 | |
| `workerId`, `date` | 연결 기준 (같은 작업자·같은 날짜) | 날짜는 실제 달력 날짜인지 검사 |
| `plannedStart`, `plannedEnd` | 예정 시작·종료 `HH:MM` | 00:00~23:59, 종료가 시작보다 늦어야 함 |
| `status` | 예정 · 진행 중 · 완료 · 취소 | 취소는 판정 제외, 이미 시작된 후속 일정은 '해당 없음' |
| `actualEnd` | 실제 종료 | 완료 일정에서 최우선 |
| `expectedEnd` + `expectedEndSource` | 예상 종료와 출처 (**현장 보고** / **관리자 입력**) | 화면의 '예상 종료 입력'으로 넣음 |
| `travelMinutes` + `travelSource` | 직전 현장에서 오는 이동 필요시간과 출처 (**입력값** / **데모 가정값**) | **실시간 교통정보 아님**. 없거나 음수·NaN이면 '누락' |
| `travelFromId` | 이동시간 출발 현장 (알 때만) | 연결된 선행 현장과 다르면 판단 보류 |

옵션 `asOf` (`YYYY-MM-DDTHH:MM`) — 데모 화면은 고정된 데모 기준시각 `2026-07-28T10:40` 을 넘깁니다. 실제 시계는 쓰지 않습니다.

## 5. 판단규칙 (`RISK_RULES`, 버전 `chain-risk/1.0.0`)

| ID | 규칙 |
|---|---|
| R1 연결 | 같은 작업자·같은 날짜의 취소되지 않은 유효 일정을 예정 시작 순으로 연결한다 (동시각이면 종료·id 순 — 결과가 입력 순서와 무관) |
| R2 종료시각 결정 | 실제 종료 > 예상 종료(현장 보고·관리자 입력) > 추정 규칙 > 예정 종료. 출처를 함께 남긴다 |
| R2-1 추정 규칙 | 진행 중인데 기준시각이 예정 종료를 지났고 종료·예상 보고가 없으면, 종료시각을 최소 기준시각으로 본다 |
| R3 예상 도착 | 선행 예상 종료 + 이동 필요시간 |
| R4 여유·부족 | 후속 예정 시작 − 예상 도착 (아래 등급표) |
| R5 연쇄 전파 | 후속 예상 시작 = max(예정 시작, 예상 도착). 작업시간을 유지해 예상 종료를 다시 계산하고 다음 연결에 쓴다 |
| R6 시간 중복 | 같은 작업자의 예정 시간이 겹치면 '매우 높음' |
| R7 데이터 확인 | 시각 형식 오류·시간 역전·날짜 오류·이동시간 누락·취소로 인한 이동 기준 불일치는 판정하지 않고 '판단 보류' |
| R8 시작된 일정 | 이미 진행 중·완료인 후속 일정은 사전 판정에서 뺀다 ('해당 없음') |
| R9 자동 변경 금지 | 권장 확인 항목만 돌려주고 일정·담당자를 바꾸지 않는다 |

### 위험등급 (R4, `THRESHOLDS`)
| 여유(분) | 등급 | 위험으로 셈 |
|---|---|---|
| 10 이상 | 없음 | 아니오 |
| 0 ~ 9 | 주의 | 아니오 |
| −1 ~ −9 (1~9분 부족) | 중간 | 예 |
| −10 ~ −29 (10~29분 부족) | 높음 | 예 |
| −30 이하 또는 예정 시간 겹침 | 매우 높음 | 예 |

등급 기준(10분·30분)은 업무 판단을 위한 **설정값**이며, 실증 데이터로 정한 값이 아닙니다. 현장 실증 후 조정 대상입니다.

### 원인 구분
`정상` · `시간 중복` · `이동시간 부족`(예정값만으로도 부족) · `선행 현장 지연`(예정값으로는 문제없으나 선행 지연 반영 시 부족) · `연쇄 지연`(선행 현장의 지연 자체가 그 앞 현장에서 전파됨) · `데이터 확인 필요` · `이미 시작`

### 권장 확인 (위험등급과 별도)
- 주의: 선행 현장 종료 예상시각 확인
- 중간 이상: 선행 현장 진행상황 확인(또는 일정 시간·이동시간 재확인) · 후속 현장 일정 조정 검토
- 높음 이상: + 대체 작업자 가능 여부 확인 · 후속 현장 고객에게 지연 가능성 안내 검토
- 시간 중복: 중복 배정 확인 · 담당자 또는 시간 조정 검토
- 선행 종료가 추정 규칙에서 왔으면: 현장에 종료 예상시각 보고 요청
- 판단 보류: 이동 필요시간 입력 / 해당 일정의 시각 입력 확인 / 이동시간 재확인

## 6. 결과 데이터

### 연결별 판정 `RiskLink`
`key`(예: `A>B`), `workerId`, `date`, `order`, `prev`(예정 종료·예상 종료·**종료 출처**·지연분), `next`(예정 시작·상태), `travel`(분·**출처**), `plannedGap`, `arrival`(예상 도착), `slack`(여유, 음수 부족), `shortfall`, `status`(판정/판단 보류/해당 없음), `grade`, `cause`, `staticConflict`(예정값만으로도 걸리는지 — 기존 `findConflicts` 와 같은 조건), `downstream`(영향받는 후속 일정), `rootId`(지연 출발 현장), `formula`(계산 과정 문장), `reason`(판단 근거), `actions`(권장 확인), `rules`(적용 규칙 id).

### 일정별 예상 시간 `ProjectedSite`
예정 시작·종료, 연쇄 반영 예상 시작·종료, 종료 출처, 시작·종료 지연분, 지연 출발 현장.

### 그 밖
- `issues` — 데이터 문제 (작업자 누락·날짜 오류·시각 형식 오류·시간 역전·예상 종료 오류·이동시간 누락·이동 기준 불일치·중복 데이터)
- `excluded` — 판정에서 뺀 일정과 이유 (취소·데이터 오류·중복)
- `diffRisk(before, after)` — 연결별 변화(신규 위험·악화·완화·해소·유지·연결 생김·연결 해제·판단 상태 변경)와 예상 시간이 바뀐 일정
- 판단 이력 `RiskLogEntry` (`src/lib/risk-log.ts`) — 순번, **데모 기준시각**, 범위 '데모 세션', 이벤트(종류·대상·입력값 변경 전후·출처·입력자), 규칙 버전, 연결 변화, 변경 전후 판정, 영향받은 일정

## 7. 실제 계산 예 — A현장 → B현장

입력: 동일 작업자, A현장 예정 종료 11:00 · 예상 종료 11:25(현장 보고) · A→B 이동 30분(입력값) · B현장 예정 시작 11:40 · B현장 상태 '예정'.

엔진 출력 (`docs/evidence/scenario-results.json` 시나리오 B, 테스트 4번):

```
A현장 예상 종료 11:25 (현장 보고)
선행 지연 = 11:25 − 예정 종료 11:00 = 25분
예상 도착 = 11:25 + 이동 30분 = 11:55
여유 = B현장 예정 시작 11:40 − 예상 도착 11:55 = -15분 → 15분 부족

위험등급: 높음   원인: 선행 현장 지연   예정값만으로 걸리는 문제: 아니오
B현장 예상 시작 11:55 · 예상 종료 12:45 (작업시간 50분 유지)
권장 확인: 선행 현장 진행상황 확인 · 후속 현장 일정 조정 검토 · 대체 작업자 가능 여부 확인 · 후속 현장 고객에게 지연 가능성 안내 검토
적용 규칙: R1 R2 R3 R4 R5 R9
```

같은 데이터에 기존 `findConflicts()` 를 적용하면 감지 결과가 **없습니다** (예정 간격 40분 ≥ 이동 30분).

## 10. 구현 완료 / 미구현 구분

### 구현 완료 (코드와 자동 테스트로 확인)
- 같은 작업자·날짜 기준 시간순 연결, 선행 예상 종료(출처 구분)·이동시간(출처 구분)으로 예상 도착·여유·부족·위험등급 계산
- 3개 이상 현장의 연쇄 전파와 영향받는 후속 일정 산출
- 취소·중복·시간 역전·날짜 오류·시각 형식 오류·이동시간 누락·이동 기준 불일치의 판단 보류 처리
- 이미 시작된 후속 일정의 판정 제외
- 판단 근거(입력값·계산식·규칙) 화면 표시, 권장 확인 항목 제시 (자동 변경 없음)
- 데모 세션 판단 이력과 JSON 내보내기
- 기존 `findConflicts` 대비 비교실험
- 데모 기준시각으로 재현 가능한 계산

### 부분 구현
- **대응 우선순위**: 연결별 위험등급과 권장 확인은 있으나, 여러 위험을 하나의 점수로 줄 세우는 가중치 방식은 없음. 알림은 기존 심각도 3단계 정렬을 그대로 씀
- **이동시간**: 일정에 입력된 값 또는 데모 가정값만 사용. 지도·실제 이동시간 연동 없음
- **예상 종료 입력 경로**: 통합일정 화면에서 입력. 업무보고 화면의 '예상 완료'(자유 문장)와 자동 연결되지 않음

### 미구현 (후속 과제)
- 판단 이력의 영구 저장(DB)·서버 감사로그 — 현재는 브라우저 메모리, 새로고침하면 사라짐
- 실제 사용자 계정·권한 인증, 문자·푸시 알림 발송
- 지도·실시간 교통정보 연동, GPS 위치
- 실제 운영데이터로 등급 기준(10분·30분) 검증·조정
- 현장 실증과 효과 측정 (업무 누락·일정 지연 감소 등 — 수치 없음)
